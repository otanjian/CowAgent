# 容大 AI Web 控制台菜单结构评审与优化方案

日期：2026-09-08。

范围：用户截图所示 Web 控制台、当前工作区 `channel/web` 源码，以及 `http://localhost:9899/chat` 中现有管理员会话的只读导航检查。覆盖完整侧栏、顶栏、账号菜单、首页建议卡片和主要页内导航。当前工作区包含未提交变更；本报告针对检查时的状态，不代表其他部署或 Desktop 客户端。文档是分析与设计产出，不代表产品改造已实施。

**建议将“日常工作”和“管理控制台”分开，按用户要完成的事情组织入口。先修复无反馈菜单，再明确资源和配置的职责、权限范围，最后调整布局。**

主要页内导航：

| --- | --- | --- |

| 工作空间面板 | 预览、文件 | 当前属于对话上下文；全局文件入口需要明确项目/智能体范围，不能简单给按钮换个位置 |

## 2. 问题、证据与影响

P0 表示本次菜单治理应立即处理的功能失效；不代表安全漏洞严重性。

| 优先级 | 问题 | 证据与影响 | 建议 |
| --- | --- | --- | --- |
| P0 | 5 个入口看起来可用，点击没有反馈 | 浏览器分别点击场景应用、平台设置、审计、备份升级、开放 API，当前页保持不变；源码有显式返回或缺少路由元数据 | 从正式导航隐藏；若必须展示产品规划，明确标注“筹备中”，给出说明，禁止伪装成可用链接 |
| P1 | 日常使用、开发维护和平台管理共用一棵长菜单 | 同一侧栏同时展示对话、模型凭据、记忆维护、组织角色、租户等 | 设置工作台与管理控制台两个入口；管理控制台内按实际能力展示分组 |
| P1 | “资源管理”缺少稳定分类标准 | 同时包含配置、智能体、知识、记忆和消息接入；知识的日常阅读与系统配置不是同一任务 | 拆为智能体开发、模型与接入；知识阅读进入工作台，维护功能继续按授权开放 |
| P1 | 配置入口职责重叠 | 配置页混合模型、Agent 默认参数、执行权限、访问密码、语言与通知；旁边又有智能体配置、平台设置和个人偏好 | 按对象和作用范围拆分，见第 5 节；每个设置只保留一个主要编辑位置 |
| P1 | 名称没有说明对象或动作 | “配置”“知识”“定时”“通道”“用户”“日志”等过泛；菜单“知识”和页标题“知识库”不一致 | 使用“模型与运行设置”“知识库”“定时任务”“消息渠道”“成员管理”“运行日志”等明确名称 |
| P1 | 平台与租户范围混在系统设置 | 租户列表调用平台接口，成员/角色/组织属于当前租户；所有侧栏条目静态输出，导航缺少统一能力过滤 | 平台范围与当前租户范围明确分开；由后端返回有效能力和可用功能，前端据此生成导航 |
| P1 | 页面没有可复制的独立地址 | 从对话进入配置、点击其他入口，地址保持 `/chat`；当前实现通过切换 DOM 控制视图，未找到页面导航的 History/hash 注册 | 给页面及必要的页签建立稳定地址，支持刷新恢复、前进后退和深链接 |
| P1 | 折叠菜单仍接收键盘焦点 | 浏览器收起“系统设置”，按 Tab 后焦点进入“平台设置”；父容器高度为 0，分组仍为关闭状态 | 折叠时用 `hidden`、原生折叠结构或等效机制移出焦点序列；收起时将子项焦点返回分组按钮 |
| P2 | 层级样式不统一 | “管理与监控”是静态标签，“工作台/监控/系统设置”是左侧箭头按钮，“资源管理”使用右侧箭头；子项的左缩进被 CSS 统一清零 | 分组标题使用统一语义与样式；只有可展开项显示同一种箭头；二级项保留可辨识缩进 |
| P2 | 顶栏和账号菜单重复，低频入口占据主要空间 | 租户切换、退出在两个区域出现；外观按钮与“界面偏好”打开同一类设置；语言还在配置页出现 | 顶栏保留页面定位、必要的工作区上下文及租户选择；语言、主题、通知集中到个人偏好，退出集中到账号菜单 |
| P2 | 同一账号功能出现不同交互，“关于”名称与去向不一致 | 顶栏切换租户使用菜单，账号入口使用数字输入提示框；`openAccountAbout()` 打开版本链接，HTML 默认指向 CowAgent 的 GitHub Releases | 租户切换共用一个选择器；“关于容大 AI”展示当前产品信息，版本历史使用“更新日志”，上游信息明确标注 |
| P2 | 首页卡片文案承诺与行为不同 | “查看知识库”“指令中心”实际填入提示词，用户可能期待打开页面 | 功能快捷入口明确跳转；AI 建议改为“让 AI 梳理知识库”“让 AI 介绍可用指令”，保留输入框确认发送 |
| P2 | 折叠与滚动成本偏高 | 截图中管理项已进入滚动区域；22 项全部展开需要较大纵向空间，固定品牌与账号区域进一步减少可用高度 | 优先减少当前模式展示的入口；保留现有约 240px 侧栏宽度，调整分组与留白，不依靠缩小字体塞满导航 |

权限相关结论限于菜单组织与前端入口控制。此次未切换普通成员或租户管理员账号，也未执行完整权限矩阵；不能据管理员看到菜单推断普通用户拥有后端操作权限。

## 3. 应当保留的设计

- “新建对话”是创建动作，“对话”是返回当前会话的导航，可以同时保留。输入区重复的新建按钮可以降级到菜单，但不能把返回会话改成自动创建新会话。
- “智能体”负责选择和使用，“智能体配置”负责创建和维护，拆分方向正确。建议后者改为“智能体管理”，并用位置与权限进一步区分。
- 待办记录需要完成的事项；定时任务按时间触发动作。两者保留独立入口，后续可以相互关联，截止时间不能自动等同于执行授权。
- 账号固定在底部、导航单独滚动、当前项使用背景和竖线、支持桌面收起与移动端抽屉，均有保留价值。
- 历史会话独立页面已经具有搜索与项目分组，优化导航无需推翻这套行为。

## 4. 推荐目标结构

采用两个可切换的区域。默认进入工作台；有相应管理能力的用户才看到“管理控制台”入口。切换区域只改变导航与当前视图，不创建新租户、不改变资源授权。

“工作文件”和各项后续功能是目标设计，不计入当前已实现能力，也不应在第一阶段生成新的无效菜单。首期工作台显示 6 个主要页面；管理区按角色和展开状态呈现，不把四组所有子项同时铺开。未来若场景应用数量较多，再考虑把智能体与场景汇总为应用目录，目前不提前增加一层“应用中心”。

顶栏建议：左侧显示“当前区域 / 当前页面”，对话页补充可识别的智能体名称；右侧保留租户选择与本页必要动作。当前文件夹按钮明确标注“工作文件”。只有一个可选租户时展示租户名称即可；平台页面标注“平台范围”，避免让右侧租户选择暗示全局配置只作用于当前租户。

建议的角色边界：

| 用户能力 | 默认导航 | 边界 |
| --- | --- | --- |
| 普通成员 | 已获准使用的工作台功能 | 不显示不可访问的管理入口；知识与文件仍遵守资源归属 |
| 具有智能体维护权限的成员 | 工作台 + 对应开发维护入口 | 这是建议能力分组，不假设系统已存在独立“开发者”角色 |
| 租户管理员 | 工作台 + 本租户组织与已授权资源管理 | 不因租户管理员身份获得平台全局模型凭据或全局配置权限 |
| 平台管理员 | 平台运维和其他明确授权能力 | 平台身份不自动代表可读取全部租户的业务文件、历史和待办 |

## 6. 交互与实现建议

1. **统一菜单登记。** 以一份导航元数据生成侧栏、页面标题、分组、面包屑和地址；字段包括稳定 ID、名称、父级、URL、页面加载器、可用状态、权限能力和作用范围。避免 HTML、`VIEW_META` 和二次覆盖的 `navigateTo` 分别维护名单。
2. **先验证导航，再离开页面。** 未知入口、未开放入口、无权限入口应在清理当前页之前处理；所有导航来源复用同一未保存编辑保护，保护通过后才开始目标页加载。
3. **建立真正的页面地址。** 现有原生 JS 可先用 hash 路由，如 `/chat#/workbench/history`、`/chat#/admin/agents`，不要求为菜单改造重写前端框架。保留旧 `/chat` 入口，处理未知地址、刷新和浏览器前后退；资源访问仍由后端验证。
4. **统一折叠行为。** 选中子页时展开所属分组并滚动到可见位置；关闭后子项从焦点序列和可访问树移除。桌面图标模式有名称提示，移动端使用同一导航数据。
5. **明确四种状态。** 可用、功能未开放、无权限、加载失败不能共用空白页面或“暂无数据”。未开放功能默认不展示；明确可申请的权限才提供申请说明。
6. **保留业务上下文。** 导航重排不能改变会话归属、智能体、租户、项目、草稿和后台执行；从智能体目录开始新会话继续与“返回对话”区分。切换租户时更新权限与导航，处理旧页请求迟到问题。
7. **先拆区域，再调密度。** 常用菜单行高可维持约 40–44px，分组间距统一，二级缩进约 12–16px；宽度延续现有约 240px。图标模式保留清晰提示，不能只用缩小字体或缩窄侧栏解决入口过多。
8. **首页提供清晰动作。** “打开知识库”跳转页面，“让 AI 梳理知识库”填写任务草稿。工作文件若尚无独立页，入口应继续打开当前对话的文件面板并说明范围。

## 7. 实施顺序与验收

### 第一批：消除立即可见的问题

- 隐藏 5 个无效入口，或为明确需要保留的规划项提供不可误解的状态说明。
- 修复折叠组的隐藏焦点；统一箭头方向和二级缩进。
- 改名：知识→知识库、定时→定时任务、通道→消息渠道、智能体配置→智能体管理、日志→运行日志、用户→成员管理。
- 首页建议文案与实际填写草稿行为一致；账号菜单集中退出，个人偏好入口命名统一。

验收：没有无反馈导航；折叠分组后 Tab 不进入隐藏子项；菜单与页面名称一致；已有会话及配置的使用行为保持有效。

### 第二批：完成导航与职责重组

- 落地工作台/管理控制台两个区域和单一导航元数据。
- 增加页面地址、刷新恢复、浏览器前后退和未保存编辑保护。
- 依据后端能力与身份模式显示入口，区分平台与当前租户范围。
- 拆分配置职责，先明确配置来源与继承，再迁移编辑位置。

验收：普通成员仅看到被授权的日常功能；租户管理员不会因布局变化获得平台权限；平台管理员明确知道操作作用范围。任一可用菜单都有独立可恢复地址，切换后恰有一个当前项；所有旧入口都有明确迁移结果。

### 第三批：按业务需要补齐功能

- 建立有明确范围与授权的工作文件页；补待办与定时任务、执行记录的关联。
- 场景应用、审计、备份升级、开放 API 逐项完成业务与权限验收后再进入主导航。
- 只有菜单规模与实际使用数据证明有必要时，再加入全局菜单搜索或收藏；避免让用户依赖搜索才能找到基础功能。

建议进行 5 个找入口任务的可用性验证：继续昨天的对话、找采购知识资料、新增个人待办、修改某智能体能力、给同事分配角色。目标为用户不需先猜“资源管理”或“配置”的含义即可找到入口。记录完成率、点击路径和误入页面次数，先建立基线再评估收益，不预设已实现的提升比例。
