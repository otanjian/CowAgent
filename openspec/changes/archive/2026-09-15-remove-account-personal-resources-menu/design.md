## Context

目标范围见 `proposal.md`：统一移除共享账号面板中的“我的资源”及五个子菜单。本次按所有页面处理，不限定于截图的 `/admin`。

| 接入点 | 当前行为 | 改动边界 |
| --- | --- | --- |
| `channel/web/chat.html` | `#account-menu-resources` 同时服务工作台与控制台，含标题、检查/重试和五个链接 | 删除完整分组及专属区域状态节点，保留账号身份和后续操作 |
| `console.js` 的账号渲染与权限刷新 | 调用 `_renderAccountResources`、`_syncAccountPersonalCurrent` 等刷新分组和高亮 | 清理专属调用、事件、重试和状态，保留通用身份与授权刷新 |
| `ACCOUNT_PERSONAL_NAV_BEGIN/END` 区段 | 同时包含个人入口适配与通用 `navigateTo`、离页保护、目标焦点逻辑 | 按引用逐项拆分，不能删除整个标记区段 |
| `console.css`、`appearance.css` | 资源项当前态、账号个人区域态与通用面板样式相邻 | 只删除无使用者的资源样式；保留移动面板、模态焦点和账号行尺寸 |
| `i18n/account.js` | 含资源分组、检查/失败/重试、个人区域、用途提示 | 更新三语用途提示并清理菜单专属键，保留个人页面的标题翻译 |
| 个人页面注册及渠道工作台 | 五个稳定 view ID 仍在使用，渠道工作台另有进行中的实现 | 页面和业务能力保持，适配菜单缺失时的导航定位 |

本次工作区存在渠道工作台的未提交改动；提案生成只写本 change 目录。实施时需要基于最新工作区逐段调整，不能恢复整份 HTML/JS 或覆盖其他任务成果。

## Goals / Non-Goals

**Goals:**

- 在所有共享账号菜单中彻底撤下该分组，重绘、授权恢复或布局切换后也不出现。
- 使剩余账号功能、焦点、移动面板和视觉间距继续完整可用。
- 保持个人页面、授权、深链接和正在开发的渠道能力，给无可见菜单入口的页面明确定位。

**Non-Goals:**

- 不删除个人智能体、渠道、记忆、工具、技能及相关配置，不删除其接口或授权编号。
- 不新增个人中心、个人导航栏或其他替代入口，不重新排列主导航。
- 不通过关闭个人能力开关或撤销角色 grant 实现菜单移除，不修改运行消费者。
- 本轮不实施代码修改，不执行归档或部署。

## Decisions

### 1. 删除共享菜单结构，不新增按页面或角色的显隐分支

从共享 HTML 删除 `account-menu-resources` 及其子节点；“账号设置”成为身份区后的第一个适用操作分组。清理该分组独占的分隔、资源状态说明和重试入口，避免出现空白区域或两条相邻分隔线。

选择结构删除，是因为要求对所有账号菜单生效。只加 `hidden` 会保留事件和焦点风险，权限刷新也可能恢复；按 `/admin` 单独隐藏会产生两个页面不一致的账号菜单。均不采用。

### 2. 按真实引用清理专属逻辑，保留通用导航

检查资源渲染、菜单点击、检查重试、区域高亮和清空状态的全部调用点，移除仅由已删除 DOM 消费的逻辑。账号本人的身份重试、退出重试、全局 `/auth/context` 获取及主导航权限刷新继续保留。

`ACCOUNT_PERSONAL_VIEWS`、`_isPersonalView` 和目标焦点函数仍可能用于直接地址及页面导航，必要时调整名称或职责而不删除其业务用途。`ACCOUNT_PERSONAL_NAV_BEGIN/END` 只是测试提取标记，其中的 `navigateTo` 和离页保护不能作为菜单代码整体清除；相关测试应改为直接覆盖保留的通用导航边界。

删除账号内当前资源项和底部个人区域状态。个人页成功进入时仍更新 `currentView`、标题和面包屑并清除其他主导航错误选中；无菜单项时不要求合成 `aria-current`。返回有菜单入口的页面恢复唯一当前项。直接进入、浏览器恢复和取消离页继续复用原链路。

### 3. 文案与可访问性随菜单内容一致调整

用途提示改为简体“账号设置”、繁体“帳號設定”、英文“Account settings”，保留真实姓名、用户名与展开状态的辅助技术描述。清理 `account_menu_resources*` 和菜单个人区域相关键前先查引用，不能删除 `menu_personal_*` 等仍被页标题使用的键。

保留桌面向上/图标列向侧面展开、移动底部面板、内部滚动、关闭按钮、Escape、焦点恢复及与顶部菜单互斥的现有行为。焦点候选从现存的可见可用操作计算，不以五个个人链接作为默认起点。

### 4. 菜单呈现与个人权限分别处理

服务端仍保留 `personal.*` 页面能力和 `nav:personal.*` 授权，直接地址继续受到原授权约束。本次的菜单省略不是 `menu_denied`，不向后端写入拒绝状态，也不通过 `member_personal_console` 等能力开关隐藏菜单。

菜单展开不再消费资源分组专用检查/重试，但不得误删其共享的授权获取函数。已有深链接与业务内入口照常访问，不在本 change 增加新的发现入口；这会降低个人页面的导航可发现性，是用户此次移除菜单所带来的明确结果。

### 5. 对齐未归档 change，避免相反的入口要求并存

当前主规范尚未合入 `move-personal-menu-to-account` 的资源入口条款，因此本次只对当前存在的 requirement 编写 `MODIFIED`，并加入菜单撤下及页面兼容的新增要求，不伪造对不存在主规范条款的删除。

实施前按当时的主规范状态重核增量；交付/归档时必须协调下列重叠点：

| 相关条款 | 最终处理 |
| --- | --- |
| 前序账号卡片用途提示、菜单展开内容及紧凑分组要求 | 合并其移动端、焦点与身份改进，删除“个人资源与设置”、五项入口及个人区域标记要求 |
| `五个个人入口统一位于底部账号菜单` | 若已进入主规范，纳入本 change 的 `REMOVED` 并说明菜单撤下、页面保留；若尚未同步，在前序同步交接中明确该条款已由本 change 取代，不能将其作为最终菜单要求 |
| `各种入口使用一致可达性` 的账号资源专用段、`账号个人入口随当前上下文更新且不预加载业务` | 保留通用授权/迟到结果/离页保护；移除要求账号恢复个人链接及分组检查状态的内容。若已同步，应将 `console-navigation-availability` 加入本 change 的受影响 capability 并给出完整增量 |
| `当前页面与层级清晰可辨` 的个人菜单唯一当前项要求 | 合并为本 change 中无菜单个人页使用标题和面包屑定位的规则，保留普通页唯一当前项 |
| `upgrade-personal-channel-workbench` 中保留账号菜单位置的要求和测试 | 协调为保留页面标识、工作台及原授权；其业务验收经已有合法入口执行，不再要求恢复“我的渠道”菜单 |

该协调是本 change 的交付任务，不是取消整个前序 change，也不是全文件覆盖。主规范若在实施期间更新，重新生成受影响增量并校验；不能只凭“后者优先”保留互相矛盾的 SHALL。

## Risks / Trade-offs

- [账号相关代码与个人导航共处一段] → 逐函数查引用，回归直接链接、跨区域导航与未保存保护。
- [权限或语言刷新重新插入菜单] → 验证结构无该分组并检查全部渲染入口，覆盖迟到上下文。
- [删翻译或样式误伤个人页、偏好子菜单] → 仅清理无其他引用的资源专用项，保留共享面板和页面标题。
- [移动面板原焦点指向已删除项] → 使用实际可见操作计算焦点，实测关闭与焦点恢复。
- [与正在进行的渠道工作台改动冲突] → 独立提交菜单增量，保留对方页面与服务实现；协调规格与浏览器测试，不回退工作区。
- [前序规格尚未归档] → 按 D5 的具体条款协调同步和重定基，归档前检查主规范不同时要求显示与移除资源组。

## Migration Plan

1. 核对当前源码、未提交改动及 D5 中前序规范状态，完成入口策略与增量协调后再实施。
2. 在同一前端版本中交付 HTML、JS、CSS、i18n 和对应测试更新，不新增数据库迁移、接口或 feature flag。
3. 验证普通成员/租户管理员/平台管理员、`/chat` 与 `/admin`、classic/split、桌面/移动、三语/主题、授权与身份恢复矩阵。现有个人运行开关保持原状态，菜单结果不依赖其开闭。
4. 使用真实浏览器记录菜单缺失、剩余账号操作、键盘焦点、旧个人链接及无额外业务请求的证据；菜单结构测试不能替代这些交互验收。
5. 如需回退，仅反向恢复本次前端菜单差异，保留其他 change 的实现、数据、权限与运行状态；不以整文件恢复覆盖并行成果。
6. 全部实施和回归完成后执行严格校验与适用增量检查，再同步主规范及归档；生成文档本身不表示菜单已在产品中删除。
