# Design: 租户编辑器统一保存与新建租户管理员账号

## 1. 范围与不在范围内

**在范围内**：租户编辑器单一保存动作（多标签一次提交）、保存时统一收集当前密码、`租户管理` 标签新建管理员账号、成员显示名可修改、以及支撑上述行为的两条归档需求修订。

**不在范围内**：租户创建表单本身（已由 `simplify-tenant-creation-form` 定型）、资源授权与租户空间投影的既有契约、平台账号的用户管理页（`平台账号` 视图）、`create_member` 的操作者权限放宽。

## 3. 统一保存

### 3.1 提交顺序

固定顺序，不随标签点击次序变化：

```
1. 租户管理员配置   POST /api/platform/tenants/{id}/admins        （不消费租户版本）
2. 资源授权        PUT  /api/platform/tenants/{id}/resources     （模型+工具合并为一次）
3. 基本信息        POST /api/platform/tenants/{id}  operation=profile
```

管理员先于基本信息是**刻意**的：`set_tenant_profile` 在 `active=true` 时要求存在有效 `tenant_admin`。若基本信息先提交，则「为新租户指派管理员并同时启用」会在第一步就返回 409 `no_admin`，操作者被迫分两次保存。把管理员放在最前使这一常见组合在一次保存内成立。

### 3.2 版本串联

每一步用**上一步响应回显的版本**作为下一次的 `expected_version`；界面在本地同步 `_tenantEditor.version` 并刷新徽标。任一 409 视为失败并按第 3.3 节处理。资源授权虽一次覆盖两类，仍只递增一次租户版本。

### 3.3 失败语义：有序、失败即停

不引入跨端点事务（三个端点分属各自事务）。约定：

- 失败时**不继续**后续步骤；已成功步骤的结果**保持提交**，不回滚（无回滚手段）。
- 未提交标签的脏标记**保留**，操作者可直接重试。
- 界面 MUST 指明失败步骤，且 MUST NOT 显示整体保存成功。
- 409 额外提示需重新加载后再提交。

取舍说明：曾考虑「尽力提交三步再汇总」，其代价是操作者更可能看到一个半提交且难以判断该重做哪一步的状态。选择失败即停，使「已提交到哪里」始终是一个前缀，便于推理与重试。

### 3.4 密码收集

- 触发条件：本次保存的步骤中**至少一步**需要近期密码（基本信息、租户管理员新建）。**仅资源授权**的保存不弹密码，因为该端点不校验 `recent_password`，弹窗将不可验证。
- 密码在一次弹窗内收集，**同一次保存的所有需要密码的步骤复用同一份输入**（避免同一动作内重复输入）。
- 校验失败（401 `invalid_old`）时弹窗保持打开、原地显示可重试错误，并保留全部草稿与已选账号。
- 取消弹窗不发出任何写请求，全部脏标记保留。
- 成功后立即从 DOM 清除输入；MUST NOT 写入 `localStorage` / `sessionStorage`。

> 与既定交互的一处偏差：产品口述曾为「每个标签都弹密码」。因保存已统一为单一动作，实际等价规则改为「本批是否需要密码」。若后续确认要在纯资源授权保存上也强制弹窗，需要同时让该端点校验密码，否则该输入不产生任何安全效果。

## 4. 新建租户管理员账号

### 4.1 方案取舍

- **方案 1（采用）**：新增服务方法，在**单一事务**内建立账号 + 成员关系 + `tenant_admin` 绑定 + 审计；端点以 `mode` 区分。优点：不会出现「账号建好但没绑上管理员」的孤儿状态；建号与绑定同一审计语义；不必放宽任何既有权限。
- **方案 2（否）**：前端先调平台账号接口建号，再调 `/admins` 绑定。当前没有平台建号端点，需先补一个；且两步之间失败会留下孤儿账号，需要额外清理路径。
- **方案 3（否）**：放宽 `create_member` 的操作者校验使平台管理员可用。会把平台管理员卷入 `_require_tenant_admin` 的授权语义，并改变成员接口的越权边界，风险最大。

### 4.2 建号事务内容

沿用 `create_member` 既有契约，保证与「成员管理 → 新建成员」一致：

- `username`：全局唯一；不匹配既有用户名校验则拒绝；已存在返回 409。
- 初始密码：由平台管理员提交；必须满足长度下限且不命中常用口令表，否则拒绝。
- 账号以 `active=1`、`must_change_password=1` 建立，临时密码有效期沿用既有 3 天。
- 建立 `memberships`（`display_name` 取提交值）并绑定 `tenant_admin` 角色。
- 同一事务写审计；任一步失败整体回滚。
- 响应 MUST NOT 回显初始密码（与 `create_member` 一致：操作者已知该值，回显无收益且扩大暴露面）。

### 4.3 显示名语义修正

`set_tenant_admin` 的目标账号已是该租户有效成员时：若提交的 `display_name` 与现值不同，则更新 `memberships.display_name` 并递增该成员版本。**只改本租户成员显示名**，MUST NOT 触碰 `users.display_name`。选择模式下显示名以所选账号的显示名预填、允许修改；新建模式下显示名同时作为账号全局显示名与该租户成员显示名。

### 4.4 端点契约

`POST /api/platform/tenants/{tenant_id}/admins`

| 字段 | 说明 |
| --- | --- |
| `mode` | 可选，`existing`（缺省）或 `new`；其他值返回 400，MUST NOT 静默降级 |
| `user_id` | `mode=existing` 必填 |
| `username` / `display_name` / `temporary_password` | `mode=new` 必填 |
| `display_name` | `mode=existing` 时可选；提交则更新成员显示名 |
| `recent_password` | 两种模式均必填 |

缺省 `existing` 保证既有客户端与缓存静态资源继续可用。

## 5. 与既有归档需求的冲突处理

已归档的 `租户管理员配置入口收在租户管理标签` 含「MUST NOT 在此处新建账号或生成临时密码」，与本 change 直接冲突。处理方式：将其修订为允许双模式，并保留其既有的「MUST NOT 要求操作者手工填写内部账号标识」约束。同时 `平台直接配置管理员且不接管账号` 原文即允许「明确创建新账号」，本 change 补齐其可验收场景，使两条需求口径一致。

需求原文冲突属于产品决策而非实现细节，已在 spec delta 中显式落地；PRD 恢复后需复核（见 proposal「与 PRD 的关系」）。

## 6. 未决实施参数

- 初始密码长度下限与强校验细节沿用 `create_member` 的 `MIN_PASSWORD_LENGTH` 与常用口令表，**不新增**第二套规则。
- 密码弹窗的交互载体（复用 `openAdminModal` 还是新增轻量弹窗）留待实现时按 z-index 与焦点管理实测决定；`openAdminModal` 与全页编辑器叠加时的层级表现需先验证。
- 资源授权在统一保存中合并为一次 PUT 后，若模型与工具两类均未改动则该步整体跳过。

## 7. 测试策略

- **服务层**：建号事务的成功路径与回滚路径；用户名冲突；弱口令与常用口令拒绝；成员显示名更新且全局显示名不变；有效成员与停用成员恢复两条分支。
- **handler 层**：`mode` 缺省向后兼容；`mode=new` 参数校验；未知 `mode` 返回 400；既有 `existing` 路径回归。
- **前端契约（node:test + DOM 桩）**：脏标签收集与提交顺序；版本串联；中途失败即停与失败步骤提示；密码弹窗触发条件、取消、失败重试、成功清除；模式切换不丢内容；未选账号阻止提交；新建模式必填校验。
- **既有用例迁移**：`tests/test_tenant_tabbed_editor_frontend.cjs` 中断言「按标签独立保存」「面板内存在 recent_password 字段」的用例需按新契约改写，不得直接删除以维持覆盖率。
- 所有新增断言需做变异敏感性核验，避免恒真断言。

## 8. 迁移与恢复

无数据迁移：表结构不变，新账号复用既有写入路径。既有租户与账号不变。若上线后需回退，恢复 `_submitTenant*` 的按标签提交与常驻密码字段即可；建号能力回退只需停用 `mode=new` 分支，已建账号与成员关系保持有效、无需清理。
