## Context

动机与实测证据见 `proposal.md`。此处只记录塑造方案的在位实现与约束。

- **个人化落点**：`agent/personal_assistant.py` 的 `_personalise()`（`260`）。它做两件事——按 `_configured_aliases()`（默认 `("admin",)`）对 `AGENT.md`/`RULE.md`/`BOOTSTRAP.md` 与 `_METADATA_FIELDS`（`description`/`persona_summary`/`greeting`/`position`）做整词替换 `_whole_token_re(alias)`；然后整体覆写 `USER.md`。
- **替换是整词匹配**：`_whole_token_re` 只匹配 ASCII 词边界，因此 `admin 本人` 会被替换，而 `管理员` 作为中文词不可能命中——这正是本缺陷的机制。
- **来源是部署可变的**：`resolve_source()` 按 `personal_assistant_agent_name`（默认「智能办公助理」）在本租户内解析，也可由 `personal_assistant_agent_id` 直接指定。源模板的文案由客户自行撰写，**不得**把当前这段中文当作唯一可识别形态写死。
- **既有命令形态**：`cli/commands/management.py` 已有 `share-default-agents [--dry-run]`（`154`）与 `_preview_shared_default_corrections()`（`206`），回填入口按同一形态实现。
- **规范边界**：`user-personal-agent-provisioning`「人设个人化归属新用户」要求「别名表未命中时 SHALL 保持原文，MUST NOT 猜测或改写无关文本」。本 change 不取消该边界，而是**显式**为「归属短语」这一类字段给出可配置的生成规则。

## Goals / Non-Goals

**Goals:**

- 个人助理的 `description` 与 `persona_summary` 以**所有者本人**的身份表述，不再残留源模板的原所属人角色措辞。
- 生成规则**不依赖源文案的具体措辞**（换客户、换模板命名都成立），并保留源文的实质描述内容。
- 让**已创建**的副本也能被修正，且回填可预览、可重复、可追溯。

**Non-Goals:**

- 不改个人助理的名称（保持「智能办公助理」）。
- 不引入"猜测式"改写：不扩大别名表去做中文角色词的语义替换。
- 不改 `greeting` / `position`（无原所属人措辞）。
- 不改 `USER.md` 的既有结构与其写入口。
- 不动所有权授权、可达性与空态（`fix-private-agent-owner-reachability` 负责）。

## Decisions

### 决策 1：归属短语由「模板生成」，而不是向别名表补中文短语

新增两个可配置模板，在别名替换**之后**套用；`{name}` 取成员显示名（缺省回落用户名），`{source_tail}` 取源字段第一个 `：`/`:` 之后的内容。

- **理由**：`resolve_source()` 决定了源文案是部署可变的。若把「管理员专属智能办公助理」写进一张短语表，客户换个说法即失效，且短语表要覆盖所有可能的措辞——这是不可维护的。模板把"新所有者怎么自称"这一**部署偏好**外置，把"源文写了什么"留给运行期。
- **备选 A（向别名表补中文短语）**：把 `管理员专属智能办公助理` 等加进替换表。否决——脆且不完备；且中文不存在词边界，`管理员的`→`Rock的` 会产出 `Rock的的`。
- **备选 B（整段描述写死在配置）**：最可预测，但丢弃客户在源模板里写的实质描述，且配置里复制一份会与源文漂移。否决。
- **取舍**：`{source_tail}` 以「第一个分隔符」界定归属短语，是一个约定而非语法分析。故保留两个出口：模板留空即退回源文；不满足约定时可显式改模板去掉 `{source_tail}`。

### 决策 2：`{name}` 取显示名，而非登录用户名

- **理由**：面向人阅读的卡片文案应与既有别名替换**同源**——别名替换写入的也是显示名。用户名（如 `RC001`）是登录标识，不是称呼。
- **取舍**：需要登录名的部署可自行改模板；默认不提供第二占位符，避免过度设计。

### 决策 3：模板留空即关闭该字段的生成

- **理由**：本 change 会改变既有部署升级后的可见文案。留空是一个不改变现状的退出通道，也让"只想改描述、暂不动人设摘要"成为可配置状态，而不是又一次代码改动。
- **取舍**：默认值必须给出（即默认开启），否则本 change 对存量部署等于无效。

### 决策 4：回填只认「带私属归属的绑定」

- **理由**：`agent_bindings.private_owner_user_id` 是个人助理的**唯一判定依据**（`owned_agent_id()` 同源）。以它划范围，既不会误改来源模板与租户共享默认（它们的 `private_owner_user_id` 为空），也不需要靠名称或 id 前缀猜测。
- **备选**：按 agent_id 后缀（`-<username>`）识别。否决——那是 `_plan()` 的实现细节，不是授权记录；改名或 `-2` 后缀会漏判。

### 决策 5：回填复用既有审计动作，不新增审计通道

- **理由**：回填是对既有条目的修正，属于同一生命周期；复用 `member.personal_agent.*` 家族能让一次回填在审计里与创建/跳过可并列比较。
- **取舍**：不新增 `bulk_*` 审计动作；条目级结果足以定位。

## Risks / Trade-offs

- **升级后存量部署的文案突变** → 默认模板改变可见文案属预期；退出通道（留空）已在决策 3 给出，且 `proposal.md` 明示为需求变更而非缺陷修复。
- **`{source_tail}` 的约定误判**（源字段用「-」而非「：」分隔，或归属短语不在开头） → 误判时表现为"新文案不含源文的实质内容"或"前缀未被替换"，均为**可见**结果而非静默错误；改模板即可修正，不做语义猜测。
- **回填范围误伤** → 决策 4 以 `private_owner_user_id` 划范围，并有「不触碰非个人助理」场景与用例固定。
- **字段被人工改过** → 回填会按模板覆盖；这是"重算"的语义，且在 dry-run 可先看到全部变更条目。
- **显示名重复导致文案相同** → 属正确行为（两人同名则文案相同），不引入唯一化后缀。

## Migration Plan

- **无 schema 迁移、无列变更**。新增的只是配置项与一个管理入口。
- **存量副本**：需要显式执行回填入口才会修正；不执行则保持现状（但新建副本已按新规则生成）。
- **回滚**：把两个模板留空即回到本 change 之前的行为；回填是幂等重算，撤销配置后重跑回填即可还原为源文（在别名替换范围内的结果）。不遗留新列或新行。
- **发布顺序**：先服务端（含配置默认值），再执行回填。前端无需改动——它只呈现 `description`。

## Open Questions

- 是否需要为 `greeting` 也提供模板：当前源文（「您好，我是您的智能办公助理。」）不含原所属人措辞，无实际需求，留待出现真实诉求时再议。
- 回填入口是否需要在控制台提供入口：当前只做运维 CLI，与 `share-default-agents` 一致。
