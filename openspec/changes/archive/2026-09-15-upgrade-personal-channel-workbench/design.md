## Context

动机见 `proposal.md`。当前工作区代码已具备个人渠道服务，但界面与保存边界未形成完整流程：

| 接入点 | 当前事实 | 本次使用方式 |
|---|---|---|
| `personal-console.js` | 通用列表只渲染行级动作；渠道表单缺少目标项，身份挑战返回值未展示 | 个人渠道改由专用控制器渲染，其他个人页面保留现有流程 |
| `console.js` 的租户渠道区域 | 已有卡片、凭据字段、扫码/手工模式；DOM、草稿和请求地址绑定公共渠道 | 提取可传入容器、实例数据、字段描述与回调的展示模块 |
| `PersonalChannelHandler` / `PersonalChannelInstanceHandler` | 已有本人列表、新建、更新、启停、凭据撤销和身份关联接口 | 增补最小目标列表、创建资格、真实状态和扫码创建参数 |
| `IdentityService` 共用实例写入 | `allow_owner` 固定本人归属；`_require_instance_agent` 仅检查同租户并允许空值 | 新增共用个人目标判定，覆盖所有写入个人实例的路径 |
| 私有智能体查询 | `is_private_agent_owner` 和个人列表已有可信所有权事实 | 按同一事实生成最小候选，不加载公共管理目录作为替代 |
| 飞书注册及扫码授权 | 飞书一次性交付凭据，授权当前主要绑定 user/tenant/type，个人创建包装尚未接收授权 | 为个人扫码增加明确 scope、AuthSession、用途和目标绑定 |
| 企微浏览器 SDK | 返回 bot 凭据，没有可直接替代近期密码的服务端证明 | 填充个人表单短时草稿，显式提交并验证密码 |
| `channel/channel_instances.py` | 个人配置就绪与运行接受分离；运行接受集合为空 | 保留双层门槛，按真实个人验收逐类型登记 |

主规范为 `openspec/specs/`。`enable-member-personal-console`、`move-personal-menu-to-account` 的任务虽已标为完成，相关新增个人规范尚未归档；这里只将其作为代码及证据依赖。本 change 新增 `personal-channel-workbench` 这一交互和写入边界 capability，扫码新增要求归入现有 `channel-scan-onboarding`，不复制个人渠道全生命周期规范。

## Goals / Non-Goals

**Goals:**

- 使用同一套渠道展示与凭据字段定义，保持独立的个人和公共请求上下文。
- 将本人私有目标约束落实到实际持久化、启动与消息消费，页面候选与服务端校验保持一致。
- 形成选择目标、接入凭据、配置保存、本人消息身份关联和状态查看的完整流程。
- 使用现有身份库、凭据、审计、配额及实例运行管理能力，保留恢复和关闭路径。

**Non-Goals:**

- 不改变菜单位置、公共渠道语义、其他个人资源页或智能体创建/发布模型。
- 不让个人智能体向其他成员、陌生人或群聊开放，不新增公共实例上的个人路由配置入口。
- 不新增渠道供应商、不重写微信扫码或原生 Desktop 协议，不承接兄弟 change 的真实微信/Desktop 验收。
- 不以页面交付替代真实渠道验收，不全量开启当前八种多实例类型，不重写审批、凭据或审计引擎。

## Decisions

### 1. 共用展示模块，分别持有页面控制器和请求适配器

新增小型渠道展示模块（建议 `channel/web/static/js/channel-workbench.js`），提取现有卡片外壳、类型图标、凭据字段和表单模式切换。公共页面仍由其当前控制器提供数据与操作；个人控制器挂到既有 `personal-channels` 容器并只使用本人接口。

组件接受显式容器和回调，不读取 `channelScope()` 推断个人范围，也不共享 `tenantChannelDraft`、公共 `agentCatalog` 或固定的 `tenant-channel-*` DOM ID。个人控制器单独保存列表、候选、表单代次和轮询取消句柄。脚本装载顺序在 `chat.html` 中明确，保持其他页面的原行为。

备选方案是整页复制，开发入口较直接但容易产生两份凭据字段和扫码修复；直接重定向到公共页面则无法保证管理员进入个人页面时的固定本人语义。选择共用展示、分别请求，改造限制在渠道相关区域。

### 2. 一次个人列表响应提供工作台所需的最小投影

在兼容现有 `items`、`total`、`channel_types` 的前提下，为 `GET /api/personal/channels` 增加：

- `agent_options`：仅含当前可选本人私有目标的 ID、显示名和是否系统专属助理；不返回工作区、记忆、配置或他人名称。
- `actions.create` 与 `create_unavailable_reason`：按页面写资格、接入开关、有效租户策略、就绪类型、剩余额度及目标存在性计算，额度投影只是提示，实际创建仍执行事务内校验。
- 每类渠道的个人配置允许状态和运行状态；每个实例的原 `actions`、目标状态、身份关联和脱敏运行状态。

目标列表不直接复用完整的 `/api/agents?view=personal` 管理响应，避免工作台额外依赖智能体管理页面可达性或接收无关配置；服务端复用相同所有权事实及可用性判断。投影失败返回明确失败，不提供虚假的空候选或允许创建结论。

### 3. 将私有目标校验放入共用实例写入边界

增加单一服务层判定：目标非空、绑定租户一致、`private_owner_user_id == owner_user_id`、实际智能体存在且启用、当前 owner 可以使用。成员及租户有效性沿用现有授权链。

新建个人实例、修改目标、启用和凭据轮换调用该判定。对 `scope='user'` 的底层共用创建同样生效，不能只在 `create_personal_channel_instance` 包装层检查，因为扫码提交可直接调用共用写入。客户端提供的 owner、tenant、scope 不改变个人归属；个人入口的越权字段拒绝且不回显他人事实。

在持有写事务时复检可事务化的成员和所有权事实，结合既有版本条件、配额、应用占用、凭据与审计提交，防止检查后归属变化仍提交旧授权。Agent Registry 的存在和启用状态在提交前验证，提交后启动及每次消息消费再验，处理数据库与运行配置无法同事务提交的时间窗口。

普通改名可保留原目标；失效目标的凭据轮换和启用必须先修复，停用、撤销和解除身份关联不依赖目标合法性。更新未携带 `agent_id` 表示保留，明确提交空值不能变成默认路由。公共实例保持现有目标可空语义。

### 4. 目标绑定与本人消息账号关联分开建模

`tenant_channel_instances.agent_id` 是个人实例的唯一目标真值，工作台通过创建或编辑选择它，不引入另一份目标配置。

身份关联继续使用既有挑战及 `personal_channel_links`。工作台把动作显示为“关联本人账号 / 解除关联”，展示 `start_binding` 返回的一次性挑战、有效期和说明，并在当前页面轮询或刷新关联状态。渠道绑定和解绑请求补齐原规范要求的 `expected_version`，并在服务端统一处理，不只在界面做串行限制。

解除身份关联不清空智能体目标；本人更换目标后按现有个人路由服务同步或重建必要关联，不能让实例目标与被消费的关联目标产生两个真值。提供方连接允许按当前规则接收身份挑战，但在本人验证前不能启动业务会话。这避免“必须先能对话才能绑定”的循环。

### 5. 个人扫码独立传递范围，保留提供方协议

开始扫码前必须选择目标。飞书个人注册请求显式携带个人用途和目标，由服务端校验后将注册及授权绑定到 `(user, tenant, AuthSession, scope=personal, provider/type, purpose=create, agent_id)`。前端不构造授权；同一身份在公共页与个人页的扫码会话按范围隔离，避免互相替换。旧公共调用继续按原协议，但其缺少个人绑定的授权仅能用于原公共创建。

给个人创建处理器和服务包装增加 `scan_ticket`，共用写入从可信入口及授权记录验证预期范围和目标。票据只替代创建时的近期密码，不授予编辑、类型开放或目标使用权。成功创建才消费，失败保留有效授权；沿用飞书重复提交被拒的契约，不照搬微信的持久幂等回执。

飞书成功回调自动保存到个人接口并刷新列表，名称按现有类型与应用末四位派生。企微 SDK 只填充个人草稿，仍由用户提交并验证近期密码。已有实例编辑使用原更新接口和密码验证，不以创建授权轮换已有凭据。

同一表单内模式切换保留草稿；换目标则取消当前个人扫码，重新校验目标后重新发起。取消、离开、切换租户、退出或登录失效立即清理短时秘密、计时器及回调资格。采用请求/表单代次检查和实际取消机制共同处理不支持取消的供应商回调。服务端注册领取继续校验发起登录会话。

本次不扩展部署支持形态；若现有扫码状态存储不能满足当前多 worker 隔离要求，该扫码动作保持未开放，工作台提供说明及获准的手工接入，不因新增页面改变前置门槛。

### 6. 配置、连接、身份与可对话分别投影

保留现有开关：`member_personal_console` 控制个人页面，`personal_channel_onboarding` 控制新接入及适用配置动作，`personal_channel_runtime` 与 `PERSONAL_RUNTIME_ACCEPTED_TYPES` 共同控制个人运行。租户允许类型及治理停用继续参与最终判定，不新增第二套运行白名单。

| 条件 | 工作台呈现 |
|---|---|
| 配置已保存，运行总开关或类型未开放 | 已保存 / 运行未开放，说明具体原因 |
| 目标不合法 | 待修复目标，禁止恢复运行 |
| 类型已开放，连接进行中或失败 | 连接中 / 连接失败，针对原实例重试 |
| 提供方已连接，尚无本人身份关联 | 已连接 / 待关联本人账号，业务对话不可用 |
| 提供方已连接、关联有效、目标有效且授权通过 | 可对话 |
| 本人或治理停用 | 已停用及对应原因 |

状态来自现有运行管理器和当前授权事实；未知状态显示待确认，不以 `active=true` 合成已连接。`runtime` 应用失败不撤销已提交的配置，但对界面返回明确失败及恢复方式。保存响应丢失时刷新本人列表核实，不盲目再建同一应用。

首批真实运行验收固定为 `feishu` 与 `wecom_bot` 个人实例：分别完成接入、本人关联、收发、陌生人/他人拒绝、群聊拒绝、目标失效、解绑、凭据撤销及治理停用。只有逐类型证据通过后才登记接受集合；登记不自动打开部署总开关，也不扩大 `PUBLIC_PERSONAL_INGRESS_TYPES`。微信与原生 Desktop 继续由 `complete-desktop-and-scan-real-acceptance` 承接。

## Risks / Trade-offs

- [共用 UI 误用公共地址或全局状态] → 请求适配器固定范围，DOM 和草稿隔离；普通成员与管理员均覆盖真实浏览器请求断言。
- [存量个人实例曾绑定空、公共或他人目标] → 不批量改归属和目标；返回待修复状态，禁止启动，保留无目标前提的关闭操作。
- [新增目标必填导致旧客户端保存失败] → 明确为收紧个人写入契约；接口返回稳定原因，页面先升级候选与表单，安全校验不随页面回退。
- [注册成功后目标或会话失效] → 开始、领取、创建和运行分别复检；前端取消只改善体验，不作为授权依据。
- [真实渠道缺少账号、手机或环境] → 配置阶段独立验收，真实执行任务保持未完成；不得用 mock 测试解除运行门槛。
- [基线已有扫码原子性和多 worker 要求，但现有实现证据不足] → 阶段 1 明确核对；个人扫码开放前补齐其复用切片，未达到时保留关闭，不在本提案中声称已有保证。
- [尚未归档的个人规范与新边界重叠] → 对齐 `enable-member-personal-console` 的归档顺序，保留两份 change 的责任说明；本 change 仅新增工作台与更严格的个人接入目标要求。

## Migration Plan

1. **阶段 1：前置证据核对。** 核对个人实例/所有权/身份挑战/凭据/审计/配额切片和账号菜单实现；核对扫码一次性授权提交及当前部署隔离能力。记录未通过项，不因依赖任务勾选自动通过。
2. **阶段 2：服务契约。** 先完成个人目标判定、动作与候选投影、版本及运行检查，运行关闭状态下用隔离测试库覆盖合法与非法路径。预计无需新增业务表。
3. **阶段 3：工作台和扫码。** 在阶段 2 校验通过后接入共用组件、表单、身份挑战和提供方扫码；以真实 HTTP 应用及浏览器验证，外部提供方模拟结果只证明界面/契约。
4. **阶段 4：存量与配置发布验收。** 用脱敏夹具和只读盘点核对目标为空、公共、他人、跨租户、已删除和已停用实例；只由本人显式修复。合法实例不重建，不重加密全部历史凭据，不变更公共默认路由。
5. **阶段 5：真实运行开放。** 配置阶段及相关执行授权/审批依赖切片通过后，分别验收飞书和企微个人类型并保留证据，再按类型登记接受状态。外部条件缺失时保持相应任务未勾选和运行关闭。
6. **恢复。** 连接异常优先关闭对应类型运行或个人运行总开关，保存的数据保留。UI 可回退而服务端目标约束保持；不回退到把个人实例当公共实例处理的消费者。恢复时重新验证成员、目标、凭据、关联、治理和类型门槛，不自动解除治理停用。
7. **归档。** 仅在本 change 承诺的配置与两类真实运行验收完成后归档；协调前序个人规范同步，并对主规范与增量再校验。文档生成完成不是功能交付完成。
