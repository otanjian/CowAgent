# 会话注入当前登录用户身份

## Why

租户 `test15` 的「BUG 管家」需要把每条缺陷的**提出人**记为真实用户账号。实测发现运行中的智能体**拿不到当前说话人是谁**：

- web 对话链路不向智能体传递说话人：`WebMessage.from_user_nickname` 在 web 通道未被赋值，用户域目录以不透明的 `users/<user_id>/` 命名（本租户该目录尚不存在），没有任何「账号 ↔ 用户名」的映射文件。
- 系统提示里存在一个完整的「用户身份」段（`agent/prompt/builder.py::_build_user_identity_section`），但**从未被填充**：全仓库没有任何调用点传入 `user_identity=`，`config.py` 也没有对应配置项。
- 既有工具（待办、定时任务）在内部用 `svc._find_user_by_id()` 解析了用户，但**从不把用户名或显示名返回给模型**。

因此智能体只能把提出人记为「本会话用户」，或反复追问用户姓名——这与「用户只给一句话，其余自动补全」的目标直接冲突。补齐这一能力必须改动运行时代码，故以本 change 承载。

## What Changes

- **在归属单个用户的会话构建系统提示时，注入当前登录用户的身份段**（账号 `username` 为必备字段，全局显示名与租户成员显示名为可选字段）。身份**只**从已验证运行时身份（`user_id` + `tenant_id`）经身份服务解析，绝不取自工具参数、客户端字段或会话内容。
- **身份段与个人人设段解耦**：没有个人人设档案的用户同样获得身份段；身份注入不依赖任何个人文件名或内容。
- **沿用既有的会话归属守卫**：会话归属他人或归属不可验证时不注入调用者身份，避免共享/团队会话按「最后访问者」决定身份；把该守卫从个人人设注入中提取为共享助手，两处复用同一判据。
- **失败关闭**：无 `user_id`、或该用户已非有效租户成员、或身份库不可用时，不注入、不伪造、不阻断会话构建，仅记录可诊断日志。
- 不改动：`user-personal-context` 既有各项要求的语义（个人人设与个人记忆）、`self-account-context` 的 `/auth/me` 契约、任何逐请求授权与资源边界判定（身份段不构成授权依据）、`agent/prompt/builder.py` 中既有 `user_identity` 结构化段的公共签名。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `user-personal-context`: 该 capability 已规定「个人人设按用户注入」与「无用户身份时不得放行」。本 change 在同一责任域内**新增**一项要求「当前用户身份按用户注入」：会话的系统提示 SHALL 携带当前登录用户的账号与显示名，来源限定为已验证运行时身份，注入受会话归属守卫与失败关闭约束，且不得作为授权依据。个人人设是按用户注入的「偏好」，本要求是按用户注入的「身份事实」，二者共用同一注入点与同一条归属判据。

## Impact

- 代码：`bridge/agent_bridge.py`（新增身份段注入方法；将个人人设注入中的会话归属判据提取为共享助手并复用；沿用既有 `extra_system_suffix` 追加点，保持场景 → 员工 → 个人 → 身份的顺序稳定）。
- 测试：`tests/test_user_persona_injection.py`（扩展：身份段注入、无个人人设仍注入、跨用户隔离、他人会话不注入、无身份不注入、身份段不改变授权）。
- 数据：不新增 schema 迁移，不写入任何租户数据；身份段按会话构建即时读取，不落盘、不新增持久化副本。
- 消费方（数据侧，非本 change 的规范范围）：租户 `test15` 的「BUG 管家」`RULE.md` 改为以注入的账号作为「提出人」，仅在无法解析时回落为「本会话用户」。
- 授权面：不扩大任何权限。身份段是提示词中的事实描述，逐请求授权仍由既有身份服务执行。
- 兼容性：legacy（无 `user_id`）与共享/不可验证归属会话的行为与现状完全一致。
