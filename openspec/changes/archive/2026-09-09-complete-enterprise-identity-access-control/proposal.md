## Why

CowAgent 已有 User/Membership、租户角色、部门和数据库会话，当前最需要补齐的是身份安全边界和用户、角色管理的操作闭环。依据《用户、角色权限对比及实现方案》及本轮详细审查，本 change 收敛为阶段 A/B 和现有九项权限的整理；OneAgent 的技能授权、模型分配和企业登录保留为明确后续建设，不把整套运行能力改造作为本次管理功能的完成条件。

## What Changes

- 阶段 A：统一实际服务与测试工厂的 database 路由授权，按当前权威会话、账号、租户、成员和角色逐请求检查；修复审计/租户信息越权、成员编辑误重置角色和 register 归属选择，保持尚未适配消费者的服务端关闭边界。
- 补 Web Cookie 登录、来源检查、临时密码及受限会话到期、应用生命周期内的有界登录限流；身份写入和登录签发使用同连接短事务重核当前资格、密码版本与对象版本，覆盖登录和重置密码并发，成功审计与身份修改共同提交。
- 防止管理员锁定：bootstrap补有效期限与真实首次改密验收，升级前验证可用管理员；管理员重置自身改走本人改密，主动停用/降级自身时保留另一名可完成管理的管理员。
- 阶段 B：补平台账号启停、管理员资格维护和重置密码，接通四个现有管理页；复用成员查询、新建/绑定、角色和部门服务，仅补缺失筛选字段、角色回显、分页、租户管理员配置和审计交互。
- 保留现有九个权限 ID，补分组/说明等元数据，将内置角色全目录自动授权改为显式默认集合；移除通用管理员权限短路。新增小型 `/auth/context` 返回本人在所选租户的有效权限、管理资格与开放能力；零业务权限成员也能读取该摘要，不包含租户资料，`/auth/me` 保持单一本人资料来源。
- 沿用现有账号菜单及整页刷新租户切换，复用成员列表筛选显示角色/部门关联成员。独立界面工作可以并行；对应 B 接口在所需 A 认证、事务和审计切片验收后开放，不要求等待无关页面验收。
- **BREAKING（database 模式）**：旧共享密码、旧 token、URL token 不能授权；Cookie 与 Bearer 同值时兼容并按 Cookie 保护，不同值返回 400；Web 登录仅设置 Cookie，JSON 不返回可复用 token，并清理 Web 遗留 token 使用。成员更新省略 roles 保留原角色，显式空数组返回 400。未登记或未适配入口不能因管理员资格获得放行。
- 本次仅调整 change 文档，所有实现任务保持未勾选；审查时通过的 92 项精选基线测试不证明上述新增要求已经实现。

以下为**明确延期**，属于缩小本期交付范围，不是已经具备或等价完成；本期不为其预建表、接口、开关、页面或实现任务：

| 延期能力 | 后续进入条件 |
| --- | --- |
| Agent/技能/模型资源 grants、成员直接授权、模型选择策略及新增业务权限 | 明确第一个业务消费者、稳定资源标识和读取/执行迁移规则后单独设计 |
| 聊天完整运行、工具、文件/预览、离线调度委托、OpenAI API、外部通道 | 各消费者身份、资源范围、撤权及适用的 10A/08S/09G/10B/执行隔离切片真实验收；本次保持未适配入口关闭 |
| 钉钉 SSO、外部身份绑定/解绑与通道身份映射 | 选定提供方和明确绑定流程，并具备真实企业测试环境；不能用昵称或未验证的标识映射 |
| Desktop 企业登录与传输适配、桌面 SSO | 客户端与所用服务端消费者配套定义并验收；本期不新增原生登录端点或主进程代理 |
| 新 CLI 账号查询/重置等命令 | 独立明确本机维护范围及审计契约；本次 CLI 仅修 register 的精确管理员归属 |

部门数据权限、多部门、通用委派、邀请、自助注册、MFA 和未上线场景继续不在本次范围。

## Capabilities

### New Capabilities

- `enterprise-access-enforcement`: 统一请求授权、兼容凭据选择、受限会话、来源检查、即时撤权、有界登录保护及可靠身份审计。
- `account-administration`: 平台账号维护、限期密码重置、租户管理员配置、成员查询/更新语义及受信维护归属。
- `identity-management-workbench`: 四管理页的角色回显、绑定/分页/筛选、组织树、权限感知导航和审计交互。
- `business-permission-catalog`: 现有九项权限元数据、内置显式默认集合、小型有效权限上下文及延期能力关闭状态。

### Modified Capabilities

无。当前 `openspec/specs/` 正式基线为空；本次四份 ADDED 规范补齐已有产品代码的闭环，不把未归档身份规范当成已发布基线，也不重建既有身份模型。

## Impact

- 需求依据：`docs/design/user-role-permission-gap-and-plan.md` 的 G01～G09、A/B 优先包和本轮简化审查。配置引用的 `doc/优化规划/PRD/PRD-00-总目录.md`、PRD-01～12 v1.2 原文当前缺失，记录缺口并在恢复后核对真实映射，不虚构编号或阻塞已明确的修复。
- 当前证据：审查选定的 92 项基线测试通过，其中 37 项覆盖聊天 owner 边界/消费者关闭，55 项覆盖身份权限服务/撤权。聊天 handler 已补部分 owner 检查，但 Bridge 仍在 database 模式关闭运行，不能继续描述为所有 handler 都仅一行 503，也不能据此宣称企业聊天可用。实施时按目标代码版本核对；基线通过不等于新规范验收。
- 数据唯一归属：`identity.db` 保有账号、成员、角色、AuthSession、部门和身份审计；Registry、原业务库与目录继续保有 Agent 配置、会话、运行、知识和待办。仅按 A/B 需要增加最小字段/索引或版本化修正，不建设资源授权、模型策略、SSO 或离线委托存储。
- 代码范围：`auth/`、`channel/web/{web_channel,auth_handlers,admin_handlers}.py`、现有 Web 管理 JS/HTML 和 `cli/commands/management.py` 的 register。保留 Python/web.py、SQLite 和现有 Web 前端；不改 Desktop 传输架构，不复制 OneAgent 运行配置、凭据或身份数据。
- 跨 change 依赖：复用 `add-tenant-identity-access-management` 身份/事务/资源边界，`extend-sidebar-account-actions` 的 `/auth/me`、改密和刷新式切换，以及 `add-sidebar-account-menu` 的账号状态。沿用导航、Agent 工作台、独立历史页；待办仅本人和品牌存储继续由各自 change 负责。
- 交付与验收：使用一份需求→测试→版本→结果的验收表复用证据；仅当代码变更影响既有结论时重跑相关检查。对应 B 接口开放需真实 A 切片及身份事务审计证据；整体发布验证本次四份规范、现有读取/待办边界和未适配消费者关闭，不等待延期产品完成，也不将 mock 当生产依赖证据。
- 兼容与恢复：保持已有身份和业务 ID、owner 及九项权限行为；维护窗口备份并验证所需最小迁移/相容代码回退。已有 database 迁移标识后不能切 legacy 或删除标识绕过保护。归档前协调原身份等重叠规范，本次不改其他 change 的任务勾选。
