# 设计：录屏脚本

## 决策

### D1：脚本是与手册同目录的 Markdown（`webhelp/manual-video-scripts.md`）

脚本写给录制的人，不是写给使用者，因此不参与站点渲染；但它需要**入库**并且**在改手册时容易看到**，所以放在 `webhelp/manual-video-scripts.md`，与 `includes/content.php` 同目录。

候选位置的取舍：

- 不放 `webhelp/docs/`：该目录是 `tools/build-docs.php` 的生成产物，手写文件会被构建覆盖。
- 不放仓库根的 `doc/`：该目录在 `.gitignore` 里（`/doc/`），文件不会入库，脚本会随工作区一起丢掉。
- 不放仓库根的 `docs/`：那是上游 Mintlify 文档站点，往里塞本项目内部材料会污染上游目录，也会让上游同步变复杂。

**已知代价**：站点用 `php -S 127.0.0.1:8080 -t webhelp` 提供，`webhelp/` 就是站点根，因此这个 Markdown 可被按 URL 取到（`README.md` 与 `tools/*.php` 同样如此，是仓库既有状况）。脚本里只有测试账号与假数据、界面操作与旁白，不含密钥，最坏情况是暴露一份录制计划，因此接受这个代价，而不为它去占用上游文档目录或未入库目录。

相应地，规范只断言**可以真正守住**的部分：脚本不被手册页面渲染、不被链接、不成为使用者可读的手册正文；不断言「URL 取不到」——在当前 `php -S` 的部署方式下守不住。

### D2：标题前缀用 `主题.视频` 的 id，不用自然语言标题

```markdown
### `chat.compose` · 输入区控件逐个认识 · 3:10
```

理由：id 是 `content.php` 与语言包之间的稳定键，用它做锚点才能机器校验。自然语言标题会随文案调整而漂移，无法比对。标题与时长写在后面，供人快速扫读。

### D3：每份脚本四段固定结构

- **开拍前准备**：需要的账号、角色、已有数据（如「一个持临时密码的首次登录账号」）。录屏最常见的返工原因是账号状态没准备好。
- **操作序列**：编号步骤，写「点哪里、填什么、看到什么」。
- **旁白**：可以照念的话术，取自手册与能力文档里已经核对过的口径，不在这里引入新说法。
- **录制注意**：时效、脱敏、易踩的坑（如二维码过期、临时密码有效期、失败提示不区分账号是否存在）。

### D4：操作序列来自已审计的界面事实

上一版手册的 `steps` / `fields` / `note` 是从真实界面逐项核对出来的，本 change 把它们改写成操作序列，因此脚本与界面一致。合并且不再单独成片的主题（如 `preference` 并入 `account.password`）按 id 映射并入对应脚本，不丢内容。

### D5：校验覆盖，防止脚本与视频清单脱钩

`tools/check-manual.php` 增加三项断言：

1. `content.php` 的每个 `主题.视频` 在脚本文件里有且只有一个小节；
2. 脚本小节里没有 `content.php` 中不存在的 id；
3. 小节的标题文本与时长与 `content.php` / 语言包一致。

任一不满足则以非零状态退出。这样「新增一个视频却忘了写脚本」会在 CI/本地立刻暴露。

## 退出条件

- 37 个视频各有脚本，`php tools/check-manual.php` 通过。
- 脚本文件不参与站点渲染，页面无变化，页面不链接脚本。
- `openspec validate --strict` 通过。
