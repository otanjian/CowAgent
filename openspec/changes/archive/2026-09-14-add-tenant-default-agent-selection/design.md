## Context

动机见 `proposal.md - Why`。当前状态与约束：

- 租户默认已经是一个**指针**：`tenants.default_agent_id`（`auth/store.py` 已有该列），配套服务方法 `appoint_tenant_default_agent`（租户管理员）/ `set_tenant_default_agent`（平台管理员），两者共用 `_appoint_tenant_default_agent`，其中已包含「必须绑定本租户」「清除私有归属」「写审计 `tenant.set_default_agent`」。
- 写入路径已存在，读路径也已存在：`resolved_default_agent_id` 负责「已配置默认（仍可用时）→ 租户共享最小 id → 任意可用绑定」的只读解析；Web 层 `_tenant_default_agent_id` 统一委托它。
- 缺的只是**入口**：`appoint_tenant_default_agent` 全仓唯一调用点是「租户创建首个智能体时承接默认」（`_adopt_created_agent_for_tenant`），`make_default` 只存在于 `agent/admin.py`，未接路由。
- 接口层面已有一个名字相近但语义不同的东西：`POST /api/agents` 的 `action=update` 支持 `make_default`，它改的是**模板/实例级** `team.json.default_agent_id`（`registry.default_agent_id`），影响的是「默认智能体的模型跟随全局、知识库共享、不可删除」，**不改变**租户的聊天锚定。本设计只动租户默认，两套语义不得互相顶替。
- 客户端已按租户默认渲染：`/api/agents` 返回 `default_agent_id` 与每项 `is_default`，`console.js` 用其设置 `defaultAgentId`，配置页徽标、工作台排序与聊天锚定都挂在它上面。

## Goals / Non-Goals

**Goals:**
- 让租户管理员在自己的控制台里显式改租户默认，复用既有服务方法，不新增第二处写入逻辑。
- 删除默认智能体后不留失效指针，缺省解析仍按既有规则回落。
- 保证「默认」在配置页、工作台与聊天入口三处同源。

**Non-Goals:**
- 不做「个人偏好默认智能体」（每人一个默认）：放弃该路线，避免与「默认必须是租户共享」的既有约束冲突。
- 不做「取消默认」操作：清除指针即回到自动回退，本次不提供该按钮。
- 不改模板默认（`registry.default_agent_id`）的语义与其模型/知识库/不可删除规则。
- 不放开普通成员任命，不提供跨租户代设默认的入口。

## Decisions

**1. 用既有的租户默认指针，而不是在智能体上加「是否默认」布尔字段。**
字段已存在且 `is_default` 已在接口层派生；所有读路径（解析、可达性放宽、客户端徽标）都读指针。若改成每个智能体上的布尔量，就得跨智能体维护「至多一个为真」的不变量，并同时改解析与鉴权读路径。取舍：指针方案改动最小，且不会出现多真/零真的中间态。

**2. 复用 `POST /api/agents` 增加 `set_default` 动作，不新增路由。**
该 handler 已是智能体管理写操作的集中入口，已在同一处调用 `_adopt_created_agent_for_tenant` 等租户语义逻辑。新增动作可直接拿到 `ctx.tenant_id` / `ctx.user_id` 并调用 `appoint_tenant_default_agent`，无需在 `route_registry.py` 与路由基线里增条目。取舍：牺牲一点「REST 语义整洁」，换取鉴权与绑定校验只有一处。

**3. 入口放在控制台「智能体配置」详情页，作用于当前租户。**
`renderAgentDetail` 已是配置页的编辑面，且 `isDefault`（= `agent.id === defaultAgentId`）已在该处用来隐藏删除、锁定模型。把操作放这里能自然复用该判断，并让徽标即时跟随。备选是在平台管理「租户编辑 → 智能体」标签加按钮：那属于平台管理员跨租户操作面，租户管理员无法自助，本次不采用。

**4. 任命不弹二次确认。**
任命本身即 `agent-chat-launch` 已定义的「转租户共享」显式动作，且已有审计。为避免「先确认再转共享」被误读为需要额外审批，本次不加确认弹窗；副作用通过按钮文案与结果提示表达。

**5. 删除智能体时「放行 + 清指针 + 释放绑定」，而不是「拒绝删除」。**
服务端当前的删除保护只认模板默认（`agent/admin.py` 的 `registry.default_agent_id`），不认租户默认，与客户端按 `isDefault` 隐藏删除按钮的口径不一致。选定行为：服务端允许删除租户默认，删除成功后由身份侧同时清除指向该 id 的 `tenants.default_agent_id` **并释放该智能体的租户绑定**。

释放绑定不是顺手为之，而是必需：`agent_bindings` 的行目前从不在删除时清除（全仓没有解绑入口），而 `_agent_is_usable` 对注册表未知的智能体**刻意返回 True**（该函数的注释明确说明这个不对称是有意的）。因此只清指针的话，残留绑定会让 `resolved_default_agent_id` 继续把一个已不存在的智能体解析为默认——规范里「删除后回落」与「不得返回已不存在的标识」都无法成立。删除绑定行后，该智能体不再出现在 `agents_for_tenant`，解析自然回落。

实现位置放在 Web 层（删除动作成功后调用身份服务），因为租户知识只在身份服务里，`agent/admin.py` 保持无租户依赖。

**6. 默认标识同源靠「不新增第二来源」来保证。**
配置页徽标、工作台排序、聊天锚定已全部来自 `/api/agents` 的 `default_agent_id` / `is_default`，本次不新增任何客户端自算默认的分支；任命成功后强制重载目录，用服务端结果覆盖客户端缓存的 `cow_default_agent`。

## Risks / Trade-offs

- **客户端仍隐藏默认智能体的删除按钮** → 因决策 5 与既有 `isDefault` 分支，UI 上删不掉默认智能体（服务端已放行），只能先改默认再删。本次**有意保留**该客户端行为（用户已确认），作为已知取舍记录；若后续要 UI 也可删，需另开 change 调整 `isDefault` 分支并重算其模型/知识库锁定含义。
- **并发任命** → 两个管理员近同时任命不同智能体时，后写入者胜出，租户默认可能不是其中一方预期的那个。单事务内 `UPDATE tenants` 保证不会出现中间态；审计 `tenant.set_default_agent` 提供追溯。
- **清理指针需按智能体反查租户** → 需要对 `tenants.default_agent_id` 执行按值更新的全表扫描，并删除 `agent_bindings` 中该智能体的行。当前租户规模下可接受；如租户量增长明显，再评估索引。
- **删除会释放租户绑定** → 与修复前相比，被删智能体不再残留在 `tenant_agent_ids` 中，因此管理侧列表、成员可见集合会立刻少一项。这是期望行为（智能体已不存在），但会让「先删后想恢复」只能靠重建智能体 + 重新绑定。
- **私有归属被清除后不可自动还原** → 共享转换是单向的，原私有归属不记录在绑定上。审计保留操作者与目标，可人工重建；如需更强可回滚性，需要额外的归属历史，本次不做。
- **模板默认与租户默认可能重合** → 当被删/被改的智能体同时是模板默认时，模板默认不可删除的既有规则优先，删除仍被拒绝，不会产生脏指针。
- **存量失效指针** → 本次不做批量数据校正。解析路径本就跳过失效配置，因此不阻塞使用；清理只覆盖「本次之后的删除」。

## Migration Plan

- 无表结构变更，无数据迁移，不需要停机步骤：`tenants.default_agent_id` 列与相关服务方法均已存在。
- 上线顺序：先接口、后前端。旧前端在接口存在前后行为不变（不调用 `set_default`）；新前端在旧后端上调用会得到未知动作错误，界面保持原默认并给出失败提示。
- 回滚：撤掉新增动作与按钮即回到当前行为；已写入的租户默认是既有语义的数据，不属于需要回滚的临时状态。

## Open Questions

- 是否把同一操作也补到平台管理「租户编辑 → 智能体」列表（便于平台管理员为任意租户代设默认）留待后续 change；本次入口只在租户自助的控制台配置页，不影响本设计成立。
