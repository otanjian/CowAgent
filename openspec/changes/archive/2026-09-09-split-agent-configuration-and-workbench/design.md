## Context

动机与范围见 `proposal.md`。当前实现具备以下接入点：

- `channel/web/chat.html` 的 `data-view="agents"` 位于工作台；`view-agents`、`agents-grid` 和详情抽屉组成配置页，包含概况、能力、核心文件及创建表单。
- `console.js` 的 `VIEW_META.agents` 归属工作台；`navigateTo()` 在进入该页时加载目录、收起历史面板，离开时关闭配置抽屉。`loadAgentCatalog()` 同时刷新管理数据、选择器和活动智能体，不能直接作为无副作用的工作台启动校验。
- `/api/agents` 默认 GET 返回 `AgentAdminService.snapshot()`，含智能体配置、工作空间、通道实例和 `revision`。写操作已有配置版本冲突机制。
- `startChatWithAgent()` 当前先改变活动智能体，再调用 `newChat()`，而未保存文件确认位于 `newChat()` 内；取消后可能留下部分切换状态。现有另一些智能体切换入口会调用 `resetWorkspaceToAgentRoot()`，当前详情页入口未显式执行该步骤。
- `AgentRouter` 已对显式不存在或停用的 `agent_id` 报错；应复用该约束。Desktop 通过独立 React 页面与同一默认 API 管理智能体，不属于本次新增页面范围。
- 身份 change 尚为提案，不能假定 database 授权与运行适配已经落地；现有工作区也有其他改动，实施时应局部合并。

## Goals / Non-Goals

**Goals:**

- 用独立使用视图承载卡片浏览，复用原配置编辑器和原聊天链路。
- 将列表读取与聊天状态修改分开，只有校验和离开确认成功才提交会话切换。
- 保持配置、智能体 ID、会话、历史和工作空间的唯一归属及既有客户端兼容。

**Non-Goals:**

- 不建设智能体市场、发布流程、独立详情应用、第二套聊天运行时或新的业务数据库。
- 不改造 Desktop 导航，不实施整个租户身份体系，不通过本次入口建设解除既有运行限制。

## Decisions

### 1. 保留配置视图标识，新增工作台视图

保留 `agents` / `view-agents` 作为配置页内部标识，将其菜单移动至管理并新增 `menu_agent_config` 文案；页面标题改为「智能体配置」。工作台新增 `agent-workbench` / `view-agent-workbench`，继续使用 `menu_agents` 表达「智能体」。

| 入口 | 视图标识 | 面包屑 | 内容 |
| --- | --- | --- | --- |
| 工作台 → 智能体 | `agent-workbench` | 工作台 / 智能体 | 已配置智能体卡片、简介、开始对话 |
| 管理 → 智能体配置 | `agents` | 管理 / 智能体配置 | 现有配置列表及详情编辑器 |

保留内部标识可让 `openAgentCreateFromComposer()` 和 `openAgentCreateFromModal()` 等既有管理跳转继续成立。相比把原 `agents` 改成使用页，可以减少创建入口和测试的语义迁移。Web 仍使用当前 `/chat` 单页面导航，不增加 URL 路由体系。

两个目录页面进入时收起历史面板，离开目录返回聊天时恢复原先偏好；相邻目录切换不得覆盖最初的面板状态。沿用原配置抽屉关闭规则，并分别补齐三语文案与窄屏布局。

### 2. “已配置”沿用当前保存及启用状态

工作台展示已经保存且 `enabled` 的可见智能体；默认智能体也属于正常可用项。未保存表单不是配置数据，已归档/停用项只在配置管理里保留。没有独立发布状态，不用职责、头像或独立模型是否填写作为上架门槛，允许跟随全局模型配置。

卡片仅展示头像、名称、职责简介、默认标识和「开始对话」。名称和简介作为文本安全渲染。可运行卡片主体与按钮触发同一动作，使用可键盘操作的结构，避免嵌套按钮或冒泡重复启动。单智能体时保留工作台入口，并在进入后的聊天中明确展示选中身份。

本期不增加搜索、标签分类或完整详情页；介绍直接来自现有 `description`。这样无须为简单使用入口扩展配置模型。

### 3. 为同一目录提供最小读取投影

在现有 `AgentsHandler.GET` 增加显式 `view=workbench` 读取表示；不携带该参数时维持旧响应。工作台投影从同一配置/Registry 数据来源生成，返回以下内容：

```json
{
  "status": "success",
  "agents": [
    {
      "id": "purchase-assistant",
      "name": "采购助手",
      "description": "了解采购流程并协助处理采购问题",
      "avatar": null,
      "is_default": false,
      "can_chat": true,
      "unavailable_reason": null
    }
  ]
}
```

仅返回已启用且可读项。`can_chat` 表示当前身份模式允许进入聊天，不代表模型凭据或外部服务健康检查通过；模型运行失败仍按既有聊天错误处理。`unavailable_reason` 为可本地化的稳定原因码，例如 `runtime_not_enabled`，不能暴露内部配置。

字段使用白名单，不返回完整配置后再由浏览器裁剪；尤其不包含 workspace、channel_instances、核心文件或模型配置。默认标识在可见项内计算，不返回不可见默认智能体 ID。上传头像复用现有头像接口及成功刷新后的缓存更新方式，不新增头像存储。

`legacy` 模式延续当前 `_require_auth()` 策略。若身份 change 已落地，则工作台读取接入其真实 `agent.read` 与资源范围解析，头像读取遵循相同范围；未开放的管理与运行接口维持关闭。前端通过 `can_chat` 改善交互，但服务端鉴权独立执行。整个应用在 database 下的管理快照访问和后台初始化必须遵守身份 change 的既有关闭/过滤策略，不能仅靠新增投影声称全站隔离完成。

使用独立工作台列表状态，不直接调用会修改 `activeAgentId` 的 `loadAgentCatalog()`。每次进入或手动刷新读取最新数据；请求序号和页面/身份上下文共同约束响应应用。配置页不维护第二份数据，只让下次列表读取失效并刷新。失败显示重试、禁用过期卡片；成功空响应显示空态，二者分开。

相比单纯复用完整管理快照，这个增量投影避免工作台获得多余管理数据，同时保留旧客户端契约；无新增存储或运行依赖。

### 4. 以一次受保护的切换进入既有聊天

整合或扩展 `startChatWithAgent()`，让配置页和工作台入口共用可靠的指定智能体启动流程：

1. 记录用户点击的目标 ID，设置启动中的防重复状态；在任何全局状态修改前完成现有未保存内容保护。
2. 重新读取工作台目录或调用同等无副作用校验，确认目标仍在可读启用列表且 `can_chat` 为真。校验只接受显式点击的 ID，不选默认替代项。
3. 提交前核对用户仍处于本次启动上下文；若已导航离开、身份改变或取消，丢弃结果并保持旧会话。
4. 同步提交活动智能体和新会话，明确使用不继承项目的路径（结合当前 `newChat(..., inherit=false)` 行为核对），并重置到目标 Agent 根工作空间、清空新会话成员与会话级覆盖。调整 `newChat()` 的结果反馈或拆分确认/提交阶段，防止二次确认取消后出现部分切换。
5. 导航到现有 `chat`，更新目标名称与头像，展开必要的会话区域并聚焦输入框；首条消息沿既有链路显式携带目标 `agent_id`。不自动生成或发送开场消息。

对目标启动使用一次性在途保护，快速双击只产生一次切换；离开页面后迟到结果不能抢回导航。新会话遵循现有延迟持久化规则，不因仅点击入口强行新增数据库记录。

服务端首条及后续消息继续校验显式目标和当前授权，处理校验后目标又被删除/停用的竞态。前端目录刷新不能把这个已绑定会话静默改为默认 Agent；只在明确的新会话选择中采用默认回退。保留其他会话的后台流式任务与历史绑定。

相比单纯复用当前详情页函数，这里补齐启动顺序和工作空间归属；不改写运行时路由、模型调度或会话数据库格式。

### 5. 按现有身份模式验收，避免扩大依赖

阶段 A 对齐实际导航、Agent 读取和聊天能力，记录 PRD 映射缺口及跨 change 菜单差异。阶段 B 实现 Web 双入口和 legacy 部署中既有运行能力的完整使用闭环。阶段 C 完成兼容性、数据无迁移验证与模式验收后交付。

本次不引入独立 feature flag，沿用现有身份模式和运行消费者关闭策略。若交付环境仅为 legacy，则真实验证该模式；若启用 database，必须先取得身份域读取/隔离切片证据，再验证工作台可读及运行关闭，不能用 mock 权限或解除全局开关代替验收。database 的实际运行开放留给相应消费者适配，不要求本 change 实施新的 10A/08S/09G/10B 子系统。

## Risks / Trade-offs

- [原配置目录加载会修改活动 Agent] → 工作台加载独立且无切换副作用，重新检查会话绑定后的默认回退逻辑。
- [编辑器取消离开后已经换了 Agent] → 先保护、再验证、最后同步提交；加入取消后完整上下文不变的回归场景。
- [配置在另一标签页修改，或两次刷新返回乱序] → 进入和启动时重新读取，应用请求序号与上下文检查；服务端在消息执行前再次校验。
- [新投影改变老客户端行为] → 无参数响应和管理写入原样兼容，单独验证 Desktop 的默认读取契约。
- [导航草案和待办 change 修改同一区域] → 保留本次外所有菜单；归档时合并 `platform-navigation` 的管理菜单要求，消除旧“不含智能体”与新入口矛盾。
- [PRD v1.2 原文缺失] → 以本次明确用户范围为依据并记录缺口；原文恢复后核对增量归属，不宣称整个 PRD 完成。

## Migration Plan

1. 实施前记录现有菜单、Agent ID、配置版本及会话/工作空间引用作为比对基线；保留工作区其他改动。
2. 同批发布增加读取投影的后端与新增工作台的 Web 资源。旧前端对默认 `/api/agents` 的调用继续工作；新前端遇到不支持投影的旧后端应显示明确错误，不静默消费完整管理快照。
3. 验收配置创建/编辑、列表更新、A 到 B 的聊天启动、首条消息归属及模式边界。此变更不搬目录、不重写 Agent ID、不迁移会话数据库。
4. 回滚时恢复本 change 的 Web 视图与读取扩展即可；已有配置和新产生的会话仍使用原数据结构，不删除或回滚用户业务记录。
5. 实施及验收后再归档规范，按最终双入口结果同步导航主规范；本次仅产出方案，以上能力尚未实施或测试。
